# PyPDFForm Test Suite Restructure Plan

**Date:** November 26, 2026, America/Chicago

**Tracking issue:** [PPF-2145](https://github.com/chinapandaman/PyPDFForm/issues/2145)

**Evidence baseline:** Commit `7716d1ae8945767b7065fd53d323b3dffdc554bf`, package version `6.3.0`

**Deliverable:** Four phases, one pull request each. Completed phases record their implementation and validation below.

The issue holds the full design: the target layout, where each of today's tests goes, and the `expect_pdf` fixture. This file tracks the phases, the maintainer's decisions, and the evidence for each phase. The issue body and its acceptance criteria stay as filed. Progress after each merged pull request goes in a "Progress after #N" comment on the issue.

## How to use this file

Each phase's pull request updates that phase's entry in the style of the [action plan](2026-10-10-PyPDFForm-Action-Plan-by-Effort-Level.md). It sets **Completed**, **Confirmed policy and scope**, **Validation**, and **Remaining limitations**, and adds one bullet per maintainer review round. Confirm the decisions a phase needs, one at a time, before it starts, and record the outcome in the decision table.

No phase removes a test or regenerates an expected PDF. Each phase keeps every expected PDF byte for byte and keeps 100% statement coverage.

## Baseline

Measured at the baseline commit on macOS arm64 with 10 cores, `./venv` with Python 3.14.10, and standard zlib:

- 46 test modules, 18,657 lines, 593 test functions, and 1,151 collected tests. `tests/test_functional.py` (4,452 lines, 303 tests) and `tests/test_widget_attr_trigger.py` (3,898 lines, 476 tests) held 45% of the lines and 68% of the tests.
- 263 test functions compared output with an expected PDF in three ways: inline `len` and `==` checks, `assert_same_pdf`, and `skip_regenerate` with a length check. Each recorded its output for regeneration by hand in `request.config.results`. 18 library tests and 19 doc example tests also made semantic assertions on the output they compared.
- 63 helper functions were defined in test modules. `tests/test_generate_appearance_streams.py` imported a helper from `tests/test_need_appearances.py`. `tests/conftest.py` had 729 lines and 38 fixtures.
- `pdf_samples` held 258 tracked files (106 MB): about 193 expected PDFs, 64 inputs, and `fixture_environment.json`. Inputs and expected PDFs shared directories.
- The suite took 57 s serially. In `master` Tests run [45866630502](https://github.com/chinapandaman/PyPDFForm/actions/runs/45866630502), the pytest step took 109–353 s per job across 15 jobs. `make compare-pdf-diffs` and `make generate-new-pdf-samples` ran 1,025 non-CLI tests to write 188 PDFs. No two tests had identical bodies.

## Phases

### P1 — Parallel runs

- [x] **Work:** Add `pytest-xdist` to the `dev` extra. Measure each worker with coverage and combine the data before the report. Run with `-n auto` in `scripts/test.sh`, `scripts/coverage.sh`, `scripts/new_pdf_samples.sh`, `scripts/pdf_diffs.sh`, the Tests workflow, and the nightly lowest-dependency job. Only the controller writes `pdf_samples/fixture_environment.json`. Plain `pytest` stays serial. CI prints `--durations=20`.
- **Done when:** Every Tests job passes with the coverage gate, and the pull request records each job's pytest step time before and after. A deliberately uncovered line still fails the gate under `-n auto`. A parallel `--regenerate-dir` run writes the same PDFs byte for byte, and in-place regeneration writes the environment record once. `docs/dev_test.md` documents parallel runs.
- **Basis and dependencies:** Decision 1. Independent of the other phases.
- **Baseline:** Reconfirmed at `7716d1ae`. The suite took 57 s serially with or without coverage. With pytest-xdist 3.8.0 in a scratch environment and no test changes, it took 30 s with `-n 2`, 18 s with `-n 4`, and 16.5 s with `-n auto` (10 workers). `-n 4` under coverage with `patch = ["subprocess"]` and `coverage combine` reached 100% of 3,826 statements. A run of only `tests/test_dropdown.py` failed the gate at 50%. In throwaway worktrees with a plugin that logs each write of the environment record, in-place regeneration with `-n 3` on `master` had `gw0`, `gw1`, and `gw2` each write it.
- **Completed:** November 26, 2026, in [#2146](https://github.com/chinapandaman/PyPDFForm/pull/2146). `pyproject.toml` adds `pytest-xdist>=3.8.0,<4.0.0` and sets `patch = ["subprocess"]` under `[tool.coverage.run]`. That option implies `parallel` and relies on the `a1_coverage.pth` file installed with coverage, so nothing is written to site-packages at run time. `scripts/test.sh` and `scripts/coverage.sh` run `coverage erase`, then `coverage run -m pytest -n auto`, then `coverage combine` before `xml`, `report`, or `html`. The regeneration scripts, `scripts/new_pdf_samples.sh` and `scripts/pdf_diffs.sh`, are unchanged and stay serial. The Tests workflow and the nightly lowest-dependency job run `coverage run -m pytest -n auto --durations=20 && coverage combine && coverage report --fail-under=100`. In `tests/conftest.py`, `pytest_configure` raises a `UsageError` for any regeneration (`--regenerate=1`, in place or with `--regenerate-dir`) when pytest-xdist distributes the tests, which it detects from `--dist`. The check sits next to the existing zlib-ng check. `pytest_sessionfinish` is unchanged, so the only process writes the environment record. `.gitignore` adds `.coverage.*`. In `docs/dev_test.md`, both coverage commands start with `coverage erase`. The guide also explains parallel runs and why regeneration runs one test at a time. It now says that only regenerating in place stops for zlib-ng.
- **Confirmed policy and scope:** Maintainer-confirmed: pytest-xdist is a dev dependency, `-n auto` is used in the make targets and CI, and plain `pytest` stays serial for single tests and debuggers such as `pudb` and `--pdb`. No pytest-cov. The `nightly-tests` job is unchanged, because it runs the latest tag's tests in an image built from that tag, which has no pytest-xdist until the next release. The slowest test is not changed in this phase. For in-place regeneration, the review offered two fixes: keep it serial, or stage the writes until all workers finish. Serial was chosen. With staging, a test whose input is another test's expected PDF would read the old version even after its writer had run, which would change regeneration results compared with today. For comparisons, the second review offered two fixes: keep the comparison target serial until each output has a single writer, or keep a separate artifact for each test that writes it. Serial was chosen. The single-writer fix belongs to P2's ownership rule, and without a check that fails on a second writer, a parallel comparison could break again when a new shared output is added.

In a scratch data directory with 11 worker data files left by a run that stopped before `coverage combine`, the earlier Developer Guide command passed the 100% gate on a run of only `tests/test_dropdown.py`. ### P2 — `expect_pdf` and the `snapshot` marker

- [x] **Work:** Create `tests/support/` and move the shared assertions' implementations there from `tests/conftest.py`. Convert all expected-PDF tests to `expect_pdf`, keeping their current paths, and remove `request.config.results` and `skip_regenerate` from test modules. Register the `snapshot` marker and apply it to every test that requests the fixture. `make generate-new-pdf-samples` and `make compare-pdf-diffs` select `-m "snapshot and not cli_test"`.
- **Done when:** `pytest -m snapshot --collect-only` lists exactly the tests that compare with an expected PDF. A `--regenerate-dir` run writes the same set of files as before, byte for byte, and the diff contains no PDF. No test module refers to `request.config.results`.
- **Basis and dependencies:** Requires P1. The fixture compares the way `assert_same_pdf` does: decoded objects on every platform, plus length and bytes with standard zlib. On the zlib-ng Windows jobs, tests that compare bytes inline today would compare decoded objects instead. `same_as=` keeps the CLI doc examples comparing with the library's expected PDFs without regenerating them.
- **From P1 review:** Give each expected PDF a single writer. `test_merge_using_pdf_array` and `test_fill_dropdown_via_str` use `same_as=`. Make a second writer of the same output fail the run, then run `make compare-pdf-diffs` in parallel again.
- **Baseline:** Reconfirmed at `969dbf9b` with a probe plugin that recorded, for each test, the output it registered for regeneration and every PDF under `pdf_samples/` or `docs/pdfs/` it opened. 262 test functions compared with an expected PDF, not 263 as the issue and the baseline say: 196 registered their output (194 paths, 188 written, 6 timestamped and skipped), and 66 CLI doc tests compared with a PDF that a library test owns, each with exactly one. No library test read another test's expected PDF, and no test compared with a PDF that no test registers. The only paths with two writers were `docs/test_merge.pdf` and `docs/test_fill_dropdown.pdf`. The guard in `pytest_configure` now refuses only in-place regeneration under pytest-xdist. In `docs/dev_test.md`, "Comparing with expected PDFs" replaces the `assert_same_pdf` section and covers owners, `same_as`, exit status 4, `timestamped`, `length_only`, and the marker. Its test examples use `expect_pdf`, and the regeneration paragraph says that comparison runs in parallel.
